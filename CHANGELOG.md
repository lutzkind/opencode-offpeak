# Changelog

## 0.1.9 - 2026-10-16

- **A compaction held for peak pricing is no longer lost when its hold dies.** Manual compact-first is a normal workflow: compact the session, then send the next prompt. During PEAK that compaction waits at the pre-model hook like any other request — but its hold was memory-only, so a plugin reload, a server restart, or the inactivity sweep ended it with a terminal failed compaction and, worse, left the prompt queued behind it stranded: nothing resumed at off-peak and the compaction never ran. A held compaction now persists a semantic `pending-compaction` recovery entry (with `origin: "pending-compaction"`; the raw provider request is never replayed). As soon as the recovered session is settled and idle, the plugin admits OpenCode's own compaction again; the runner keeps a pending compaction ahead of queued prompts so compact-first order survives, and the re-triggered request holds at the pre-model guard through the peak window exactly like the original. A user cancel clears the marker; inactivity and supersede keep it.
- **Recovery classes are independently owned.** A session can carry a primary `deferred`, a `pending-title` and a `pending-compaction` entry at the same time. Each `model.request` hold supersedes only its own class, and each transport-guard class (`title`, `compaction`, `primary`) removes only its own entry — a compact request can no longer clear a primary deferral or a pending title, and a `generate` request clears nothing. At the allowed window the pending compaction is admitted first, then primary continuations, then title markers, so the native compact-first order is preserved. `/offpeak status` reports `compactionRecoveryWaiting`.
- **Recovery cannot race a live execution into a duplicate.** `session.outcome` only updates at settlement, so a still-running turn reports its previous outcome; the engine now tracks live holds and the execution state from OpenCode's own `session.execution.*` events, and recovery delivery waits while either owns the session. A boundary release and a recovery admission can no longer both fire for one request (previously reachable with a stale failed outcome), and every delivery is still at-most-once.
- Evidence: 115/115 tests (99 existing + 7 cancellation tests from v0.1.7/0.1.8 + new deterministic pending-compaction coverage: the exact compact-first-then-prompt workflow, reload and restart recovery, interrupt semantics, coexistence of all three recovery classes, no class clobbering, at-most-once delivery, ordering, and the live-hold/no-duplicate guard). Real OpenCode 2.0.30 runs with a local fixture provider: compact-first through a peak window completes exactly once with the prompt behind it and zero peak-priced traffic; the same workflow with a full server restart recovers the compaction, runs it before the prompt, and completes with clean recovery state (the same harness against v0.1.8 loses the compaction and duplicates the queued prompt's continuation).

## 0.1.8 - 2026-10-16

- **A session can hold several requests at once, and cancelling cancels all of them.** OpenCode prepares auxiliary requests (the automatic title, generate, compaction) concurrently with the agent loop, so one session can have more than one request parked. The held-request bookkeeping is now per request rather than per session: `cancelHold` cancels every request of that session that is still waiting, each gets its own one-shot refusal at the transport boundary, and none can be left behind to dispatch at the next allowed window. A refusal is matched by provider, model, and request kind, and only a fresh request *of the same kind* supersedes an un-consumed refusal.
- Evidence: 107 tests pass, including a new case with a held primary request and a held title request cancelled together, each refusal consumed independently.
- Found while verifying the consuming plugin end to end: the title request and the prompt were both parked, only the newest hold was cancellable, and the title's hold could still have dispatched paid work at the window.

## 0.1.7 - 2026-10-16

- **Generic hold cancellation (`cancelHold`).** A held request can now be cancelled by whoever owns the routing decision that made it obsolete, through one new RPC method on the existing `opencode-offpeak` channel: input `{ sessionID, reason? }`, output `{ cancelled, state, model? }`. It is generic infrastructure — the plugin learns nothing about the caller — and it removes the need for a session interruption: no `session.interrupt`, no synthetic continuation prompt, no lost turn. `cancelled: true` means the hold lost the race and the request will be refused; `state: "committed"` means the dispatch decision had already been taken and the caller must wait for the next safe boundary; `state: "none"` means nothing was parked.
- **A cancelled request is refused, never sent.** OpenCode's plugin API has no typed failure channel for model requests (a hook that throws fails the whole execution), so the only supported way to hand the decision back to OpenCode is a transport failure. The hold loop therefore returns, and a one-shot refusal at `http.request` / `experimental.ws.handshake` replaces the outgoing request with a minimal placeholder aimed at a closed loopback endpoint (`127.0.0.1:1`, marker header `x-opencode-offpeak-refused`): no credentials, no provider headers, no user data, no body, and no reachable service. OpenCode classifies a retryable transport failure, and its own retry policy decides what happens next — so the same execution can continue on another route with no interruption. A refused placeholder is never re-evaluated by the pricing guard, so it cannot be held again.
- **One authoritative race outcome.** The hold state is a single synchronous transition: a hold in `holding` may be cancelled, a hold that has committed the allowed decision reports `committed` and is never cancelled. Both cannot happen, and no timing assumption is involved.
- **A refused attempt is not a provider failure.** The retry recovery added in v0.1.3 stays out of the way for a refusal this plugin itself produced: it does not register a recovery continuation for it, so the caller's resumed work cannot be duplicated.
- `/offpeak status` reports `interactiveHolds`, `armedRefusals`, `cancelledHolds`, and `refusedRequests`; a refused hold emits the ordinary `resume` event so the UI stops showing it as waiting.
- Evidence: 106 tests pass (`npm run lint`, `npm run typecheck`, `npm test`), including cancellation of a parked request (refusal armed, consumed exactly once, never dispatched), refusals that never leak onto another request, refusal expiry and supersession by a fresh hold, the committed-race result, queue-owned holds staying untouched, and the retry-recovery suppression. The consuming plugin verifies the same flow end to end against the real CLI, including a headless run that stays attached and prints the resumed result.

## 0.1.6 - 2026-10-15

- **Direct DeepSeek API support.** OpenCode exposes the direct DeepSeek API as provider `deepseek` with models `deepseek-flash` and `deepseek-v4-pro` (verified against the live 2.0.27 registry). A second built-in policy, `deepseek-api`, covers exactly those two model IDs plus the legacy aliases the provider's pricing page still accepts and bills at the Flash price (`deepseek-v4-flash`, `deepseek-v4-flash-vision-exp`). It uses the same verified weekly windows (01:00–04:00 and 06:00–10:00 UTC, Monday–Friday), the same shared Chinese public-holiday calendar data, and the same schedule evaluator as the Go policy. There is deliberately **no `deepseek-*` wildcard**: a future model that is not in the verified list stays `UNKNOWN` and fails closed with an actionable message ("not in the verified off-peak pricing policy for this release — update opencode-offpeak or add a verified custom policy").
- **Newly shipped built-in policies reach existing installs.** When a stored `offpeak.json` contains only unmodified copies of the shipped built-in policies (the state a first `/offpeak on|off` persists), missing built-in policies are appended at read time, so an existing installation gains the direct-DeepSeek policy without editing the file. As soon as anything is customized, the stored set is authoritative and nothing is added.
- **OpenCode Zen is documented, not simulated.** Zen (provider `opencode`) publishes one all-hours price per model with no peak/off-peak tiers, so the plugin deliberately installs no policy for it: requests are never delayed or blocked, and a new Zen model can never be blocked because a DeepSeek policy exists elsewhere. `pricingState` now reports flat-priced models as a distinct `FLAT` state (never waits, no transition), and the status output adds a verified provider note for Zen ("no policy needed: …"). The Zen fact (source and verification date) is recorded in `src/policy.ts` and documented in the README support matrix.
- **Immediate, non-chat feedback while a primary request is held.** When an interactive primary request enters a PEAK hold, the server emits one `rpc.opencode-offpeak.hold` event with the next allowed transition, formatted in the configured display time zone ("Peak pricing active — request held until 08:00 Asia/Bangkok. It will resume automatically in this session."). On release, or when a persisted recovery continues the session, one `rpc.opencode-offpeak.resume` event follows ("Off-peak pricing started…"). Notifications are rendered by the TUI entrypoint as toasts via OpenCode's own event stream — never as chat or model context, never in headless output. Auxiliary title/compaction/generate holds are silent, queue-owned sessions keep their existing queue/status semantics, a user cancel produces no release notification, and a hold announces only from the instance that created it, so a reload or restart cannot produce duplicates.
- **`/offpeak status` vocabulary.** The status output distinguishes `PEAK` (blocked/waiting), `OFF_PEAK` (allowed now), `FLAT` (flat all-hours price; never waits, no transition), `UNTRACKED` (no policy, explained for verified flat providers) and `UNKNOWN` (no verified policy for this model; blocked).
- Tests: 99 pass (`npm run lint`, `npm run typecheck`, `npm test`), including new provider coverage (direct DeepSeek windows, weekends and holidays, legacy aliases, unknown models failing closed, provider isolation), Zen pass-through for current and hypothetical new models, the `FLAT` state, hold/resume notification semantics (exactly one per hold, silence for auxiliary kinds, no notification after cancel, continuation notifications, no duplicates across reloads, queue-owned silence), read-time adoption of newly shipped built-in policies, and the compact display-zone formatter. Real OpenCode 2.0.27 validation with a local fixture provider covers the Go TUI toast lifecycle and status output, the direct DeepSeek hold/release with exact SSE notification counts, Zen never waiting, title generation, and reload/restart without duplicate notifications.

## 0.1.5 - 2026-10-15

- Automatic chat titles work again. OpenCode prepares automatic naming as a separate `title` model request that uses the provider's *small* model — for `opencode-go` that is `gpt-6-luna` — while the built-in policy only listed the DeepSeek models, so every title request was an `UNKNOWN` configured-provider model and failed closed at all hours. Titles stopped being generated when the plugin was installed, independent of peak pricing. The policy schema now supports `flatModels`: explicit, vendor-documented patterns for models with a single all-hours price (the Go pricing table lists peak/off-peak tiers only for the DeepSeek models). Flat models are `OFF_PEAK` at every hour, are never held or blocked, and cannot create peak-priced traffic; `models` takes precedence if a pattern matches both, and any unmatched model still fails closed. The built-in `deepseek-opencode-go` policy declares the provider's documented flat models, and an unmodified stored copy of the built-in policy adopts that list at read time.
- A held `title` request now persists a semantic `pending-title` recovery instead of being lost with the in-memory hold. A session can hold a primary continuation and a pending-title marker at the same time (v0.1.4 kept only one recovery entry per session, so a held title could shadow a primary deferral). At the allowed window the marker is delivered as a check, never a replay: a session that already has a title — generated by OpenCode or renamed by the user — clears the marker without any request, and a session that still needs one is left to OpenCode's own generation, which every interruption path (inactivity, supersede, shutdown, reload) re-triggers through the same input promotion that continues the session. `/offpeak status` reports pending markers as `titleRecoveryWaiting`.
- Recovery never mutates a session's title. OpenCode 2.0.27 exposes no plugin-facing regeneration call, and the plugin host's `session.update({ title: "" })` is not the HTTP API's regeneration — it renames the session to an empty title. The pending-title delivery therefore sends nothing of its own; a manual rename or a title generated by another process is never overwritten, and a title is never generated twice.
- The transport guard now receives the request kind and removes only the recovery class that belongs to the request that is actually crossing: a released `title` request clears a pending title, a released primary request clears a primary continuation, and neither can clear the other.
- Added deterministic regression coverage for flat-model pricing (allowed at every hour including peak windows, DeepSeek windows unchanged, overlap precedence, ambiguous and invalid lists failing closed), the pending-title marker (persistence across reload, manual-rename and already-titled safety, exact creation-time fallback still meaning untitled, child and unknown sessions, user cancel versus inactivity, at-most-once semantics across multiple reloads, coexistence with a primary deferral), and read-time adoption of the flat model list by an unmodified stored policy.

## 0.1.4 - 2026-10-14

- Peak waiting moved before the provider attempt. A normal interactive request (and a queue-owned auto task) that reaches peak pricing is now deferred at OpenCode v2's `model.request` hook, which runs while the request is being prepared and before the provider attempt (and its response-header timeout) exists.
- This removes the `Timed out waiting for response headers` failure for requests submitted during peak: no provider attempt is open for hours, no retry is required as the waiting mechanism, and the same session continues the same turn at the next off-peak transition with no synthetic continuation prompt.
- The HTTP/WebSocket transport guard remains the final hard barrier: no provider request can cross a blocked pricing window, and `queue`/`guard`/OFF behavior is unchanged (handled exactly as before by the transport guard).
- Requests that start during off-peak and cross into peak keep the v0.1.3 retry-veto recovery (retryable failure during peak → persisted same-session continuation at the boundary).
- A held primary interactive request persists a deferral while it waits and removes it on normal release, so a plugin reload or server restart during peak still delivers exactly one same-session continuation once the allowed window arrives.
- New safety net: OpenCode's `session.execution.interrupted` events are handled with origin-aware semantics. An `inactivity` interrupt of a deferred session keeps the deferral and continues the same session at the next allowed window; a `user` interrupt clears a deferral and aborts the hold; `superseded`/`shutdown` abort the hold and let the session's own recovery own the outcome.
- The built-in `deepseek-opencode-go` policy now treats Chinese statutory public holidays as full-day OFF_PEAK. The policy model supports explicit full-day OFF_PEAK exception calendars (year, dates, source URL, verification date, description), evaluated on the calendar's own time zone and overriding every weekday peak window. The 2026 China calendar from the State Council notice ships in `src/holidays.ts`; weekend make-up workdays stay OFF_PEAK; years without a calendar keep the deterministic weekly schedule; `nextTransition` skips holiday peak windows.
- Added deterministic regression coverage for the pre-model deferral (release at the scheduled boundary, zero provider traffic), passivity outside `auto`/ON/peak, untracked/unknown handling, the queue-owned deferral, deferral persistence across reload, user/inactivity/shutdown interrupts, and the full 2026 holiday calendar (periods, make-up workdays, adjacent days, `nextTransition`, calendar time zone, unknown years, validation).

## 0.1.3 - 2026-10-13

- Retryable provider/network failures that happen after peak pricing begins no longer lose the work. The plugin registers OpenCode v2's supported `retry` hook and vetoes retries while pricing is blocked (`decision = { retry: false }`), so no retry attempt reaches the provider during peak.
- A queue-owned `auto` task that fails retryably during peak moves to `WAITING_OFFPEAK` (not `FAILED`), keeps its session ID, and continues the same session at the next off-peak transition with the safe continuation prompt.
- A normal interactive session that fails retryably during peak is recorded with minimal recovery metadata in OpenCode plugin storage and continues the same session the same way. `/offpeak status` reports it as `Recovery: N session(s) waiting for off-peak`.
- Non-retryable failures still end as `FAILED`/error; retryable failures while pricing is allowed keep OpenCode's normal retry behavior; OFF, `queue`, and `guard` modes are unchanged. The continuation never replays the failed provider request, never creates a new session, and never duplicates the user prompt.
- Added deterministic regression coverage for the retry veto, the task transition to `WAITING_OFFPEAK`, the interactive recovery and its single delivery, location-scoped persistence across restart, supersede-on-new-request, non-retryable failures, OFF/queue/guard passivity, UNTRACKED/UNKNOWN pass-through, and the override case.

## 0.1.2 - 2026-10-12

- Normal interactive OpenCode requests now wait at the pricing boundary in `auto` mode instead of being discarded. The same request and session proceed automatically at the policy's next off-peak transition, with no second message, no duplicate prompt, no new session, and zero provider traffic while pricing is blocked.
- The interactive hold uses the existing shared signal and one boundary timer (`nextTransition`); it adds no daemon, scheduler, database, or polling loop, and fails closed if the plugin shuts down while a request is waiting.
- `/offpeak status` reports held interactive requests (`Interactive: N request(s) waiting for off-peak`).
- `queue`/`guard` modes still block interactive peak requests immediately, and OFF stays passive: it never releases a held request and remains no price override.
- Added deterministic manual-clock regression tests for the interactive hold, boundary release, single release, same-session preservation, OFF passivity, fail-closed shutdown, UNKNOWN/UNTRACKED handling, and unchanged queue-owned auto resume.
