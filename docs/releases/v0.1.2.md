# opencode-offpeak v0.1.2

Released 2026-10-12. `v0.1.0` and `v0.1.1` remain at their own tags and are not modified.

## Fix

- **Interactive requests no longer get thrown away at peak pricing.** In `auto` mode, a normal OpenCode message for a supported model is held at the provider transport boundary instead of failing with a pricing error. The same request and session continue automatically when the policy's next off-peak transition arrives; no second `continue` is needed, no prompt is duplicated, no new session is created, and zero provider traffic occurs while pricing is blocked.
- **The hold reuses the existing architecture.** It wakes on the shared config-change signal plus one timer scheduled for the policy's `nextTransition`, adds no daemon, scheduler, database, or polling loop, and fails closed (blocked error, no traffic) if the plugin shuts down while a request is waiting.
- **Mode and OFF semantics are preserved.** `queue` and `guard` modes still block interactive peak requests immediately. OFF stays passive and never releases a held request; a held request resumes only after the plugin is ON again and pricing allows. UNKNOWN configured models still fail closed, UNTRACKED providers keep their documented pass-through, and the queue-owned `WAITING_OFFPEAK` lifecycle is unchanged.
- **Status:** `/offpeak status` now reports held interactive requests while they wait.

## Regression protection

- Deterministic manual-clock tests prove: the guard promise stays pending during peak with zero provider transport; the release comes from the scheduled boundary itself (no new user input, status command, config edit, or external wake-up); exactly one release and no duplicate prompt or session; the same session ID is preserved; OFF does not release a held request; shutdown fails closed; UNKNOWN fails closed and UNTRACKED passes through; `queue`/`guard` do not hold; and queue-owned auto resume is unchanged.
- The server entrypoint test now exercises the real hook: hold while ON + `auto` + peak, still held after OFF, immediate block for a fresh request while OFF, `interactiveWaiting` in status, and a fail-closed rejection when the plugin shuts down.

## Install

```sh
opencode plugin add git+https://github.com/lutzkind/opencode-offpeak.git#v0.1.2
```

Then restart OpenCode (a long-running TUI keeps its old code until it restarts).

## Checks

- `npm run lint`, `npm run typecheck`, `npm test` (45 tests), `npm pack --dry-run`.
- Live validation on the supported OpenCode 2.0.26 environment with short deterministic test policies:
  - A real TUI interactive request sent during a blocked window stayed pending and its reply completed exactly at the scheduled boundary with no further input (three consecutive holds; same session; exactly one user and one assistant message each time).
  - A queue-owned task queued during a blocked window went `WAITING_OFFPEAK` and resumed automatically at the boundary in one session with one prompt.
  - An isolated single-instance TUI with a local OpenAI-compatible fixture provider showed `Interactive: 2 requests waiting for off-peak` in `/offpeak status` while held, zero fixture traffic until the boundary, and the first provider request at the boundary minute; the session ended with one user and one assistant message (the second request was OpenCode's own title generation).
  - `/offpeak status`, `on`, `pricing`, `queue`, `list`, and `remove` worked in the live TUI; the shared background service reloaded cleanly with `opencode reload` and no plugin failures.
