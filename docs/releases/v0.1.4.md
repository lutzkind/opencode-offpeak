# opencode-offpeak v0.1.4

Released 2026-10-14. `v0.1.0`, `v0.1.1`, `v0.1.2`, and `v0.1.3` remain at their own tags and are not modified.

## Fix: peak waiting no longer holds a provider attempt open

OpenCode 2.0.27 starts an attempt's response-header timeout (default 5 minutes) at attempt start, before the `http.request` hook chain completes. The v0.1.2–v0.1.3 guard held interactive peak requests inside `http.request`, so a request submitted during peak could sit in the transport attempt until the header timeout fired and the terminal showed `Error: Timed out waiting for response headers`.

The deferral now happens at `model.request`, a supported v2 session hook that runs while the model request is being prepared — after the agent/context hooks and before the provider attempt (and its timeout) exists. In `auto` mode, a peak request for a covered policy waits there; nothing reaches the provider while pricing is blocked, and at the next off-peak transition the same session continues the same turn. There is no timeout to outlast, no retry used as the waiting mechanism, no synthetic continuation prompt, no duplicate user prompt, and no new session.

- **The transport guard is unchanged and remains the final hard barrier** immediately before the HTTP request or WebSocket frame is sent. `queue`/`guard`/OFF modes still block interactive peak requests immediately through that guard, and UNKNOWN still fails closed.
- **Cross-boundary failures keep the v0.1.3 recovery.** A request that started off-peak and fails with a retryable transport error during peak still has its retry vetoed (`decision = { retry: false }`) and continues in the same session at the next allowed window.
- **Reload/restart safety.** A held primary interactive request persists a deferral while it waits and removes it on normal release; a plugin reload or server restart during peak still delivers exactly one same-session continuation once the allowed window arrives.
- **Origin-aware interrupts.** OpenCode's `session.execution.interrupted` events are handled by reason: `inactivity` keeps the deferral and continues the same session later; `user` clears a deferral and aborts the hold; `superseded`/`shutdown` abort the hold and leave the outcome to OpenCode's own recovery. No new daemon, database, scheduler, or polling loop is added — the existing signal, pump, and boundary timer drive every continuation.

## Pricing policy: Chinese statutory public holidays are full-day OFF_PEAK

The built-in `deepseek-opencode-go` policy now implements the complete pricing rule:

- Peak: Monday–Friday 01:00–04:00 and 06:00–10:00 UTC.
- Off-peak: all other hours, weekends, and Chinese statutory public holidays in full.
- Weekend make-up working days stay OFF_PEAK (weekends are always off-peak).

The policy model supports explicit full-day OFF_PEAK exception calendars (`year`, `dates`, `timeZone`, `source`, `verifiedAt`, `description`). A listed date overrides every weekday peak window for that whole calendar day, evaluated on the calendar's own time zone, so the host-local time zone never matters. The 2026 China calendar ships in `src/holidays.ts`, sourced from the official State Council notice (国办发明电〔2025〕7号, published 2025-11-04): Jan 1–3, Feb 15–23, Apr 4–6, May 1–5, Jun 19–21, Sep 25–27, Oct 1–7. `nextTransition` skips holiday peak windows (the scan covers up to 14 days so long holiday runs cannot hide the next real transition). A year without a calendar keeps the deterministic weekly schedule; no future dates are guessed. Annual maintenance is required — the State Council publishes the next year's arrangement each November.

The rule comes from the DeepSeek pricing documentation ("…excluding Chinese public holidays. All other hours are off-peak, including weekends and Chinese public holidays in full.", <https://api-docs.deepseek.com/quick_start/pricing>) that the OpenCode Go pricing page references for this provider's peak-hours definition (<https://opencode.ai/docs/go/>). A stored `policies` array that is an unmodified copy of the built-in policy adopts the built-in holiday calendar when read, so existing installations pick up yearly holiday updates without editing their config; customized policies and explicit holiday lists are preserved. The October 1–7 OpenCode Go billing comparison is not exposed per request — the provider offers only aggregate usage percentages — so upstream [anomalyco/opencode#53071](https://github.com/anomalyco/opencode/issues/53071) (open user report about National Day billing) is recorded as the cue for the annual re-check. See `DECISIONS.md`.

## Why the old error appeared, in evidence

- OpenCode 2.0.27 source: the header timeout wraps `runtime.http.execute(...)` inside the transport `execute` (`packages/ai/src/route/transport/http.ts`), and the `http.request` plugin hook is invoked inside that wrapped call (`packages/core/src/session/model-request.ts`). The timeout is `request.http?.headerTimeout ?? 300_000`ms, configured per provider.
- `model.request` is triggered in `SessionModelRequest.prepare` before `LLM.stream` is called, so no attempt timeout is running while the hook waits.
- Live reproduction: an interactive request submitted during the 06:00–10:00 UTC peak window failed exactly 5 minutes later with `provider.transport: Timed out waiting for response headers`; the v0.1.3 retry hook vetoed the retry and the recovery continued the session at the 10:00 UTC boundary. The visible error was the reported symptom; the deferral point is the fix.

## Install

```sh
opencode plugin add git+https://github.com/lutzkind/opencode-offpeak.git#v0.1.4
```

Then restart OpenCode (a long-running TUI keeps its old code until it restarts).

## Checks

- `npm run lint`, `npm run typecheck`, `npm test` (70 tests), `npm pack --dry-run`.
- New deterministic regression tests cover: the pre-model deferral released by the scheduled boundary timer with zero provider traffic, passivity outside `auto`/ON/peak and for untracked/unknown models, the queue-owned deferral continuing the same session without a continuation prompt, deferral persistence across a plugin reload, user/inactivity/shutdown interrupt semantics, and the holiday policy (every 2026 holiday period off-peak in both peak windows, make-up workdays off-peak, adjacent days normal, `nextTransition` skipping holidays, calendar-time-zone semantics, unknown years deterministic, validation fail-closed).
- Isolated end-to-end runs on the real OpenCode 2.0.27 binary with a local fixture provider and a short local policy window: an interactive request submitted during a simulated peak was deferred past the provider's configured header timeout (330s hold against a 5s timeout), produced **zero fixture requests during the peak**, was released at the boundary in the **same session**, and completed with exactly one user message, exit code 0, and no error; the same harness against v0.1.3 fails at 5s with `Timed out waiting for response headers`. A queue-owned task queued during peak waited in `WAITING_OFFPEAK`, auto-started exactly at the boundary, and completed in one session with zero peak traffic.
