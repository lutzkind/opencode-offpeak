# opencode-offpeak v0.1.3

Released 2026-10-13. `v0.1.0`, `v0.1.1`, and `v0.1.2` remain at their own tags and are not modified.

## Fix

- **Peak-aware timeout and retry recovery.** A request can start during off-peak, cross into a peak window, and then fail with a retryable provider/network error such as `Timed out waiting for response headers`. Previously the guard no longer had a pending pre-transport request to release, OpenCode's retries either reached the provider during peak or exhausted, and the turn failed terminally.
- **How it works.** The server entrypoint now registers OpenCode v2's supported `retry` hook. The hook runs after OpenCode classifies a failure and before any retry is scheduled. When the plugin is ON in `auto` mode, the failure is retryable, and the policy blocks the model, the plugin sets `decision = { retry: false }`, so no retry attempt reaches the provider, and records the recovery:
  - A queue-owned task in `RUNNING` moves to `WAITING_OFFPEAK` (not `FAILED`) and keeps its session ID; the existing pump resumes it at the next allowed window with the safe continuation prompt.
  - A normal interactive session is recorded with minimal recovery metadata (session ID, provider/model, location) in OpenCode plugin storage; at the next allowed window the engine sends the same safe continuation prompt into the same session. `/offpeak status` reports `Recovery: N session(s) waiting for off-peak`.
- **Safety preserved.** The continuation never replays the failed provider request byte-for-byte, never creates a new session, and never duplicates the user prompt. Non-retryable failures (`provider.invalid-request`, `provider.auth`, `provider.quota`, `provider.content-filter`, …) still end as `FAILED`/error. Failures while pricing is allowed keep OpenCode's normal retry behavior. OFF, `queue`, and `guard` modes are unchanged, `run-now` override semantics are unchanged, UNKNOWN still fails closed, UNTRACKED still passes through, and ambiguous `RUNNING`-after-crash recovery still requires an explicit retry. No new runtime, scheduler, database, daemon, or polling loop is added.

## OpenCode retry lifecycle evidence (2.0.27)

Measured with the real 2.0.27 binary and a local provider fixture:

- A withheld-response header timeout produces `error.type = provider.transport` and the default retry decision `{ retry: true, delay }` with jittered exponential backoff; the retry hook is called with `attempt` 2, 3, 4 and then `{ retry: false }` at attempt 5 (three retries, four physical attempts total).
- HTTP 500/503 (`provider.internal`) and 429 (`provider.rate-limit`) are retryable the same way; HTTP 400 (`provider.invalid-request`) is terminal at attempt 2 with `{ retry: false }`.
- Every retry attempt re-enters the full hook chain (`context` → `model.request` → `http.request`), so the pricing guard still sees every physical attempt.
- The header-timeout clock starts when an attempt starts, before the hook chain completes, so a guard hold longer than the provider's header timeout would time out while held; the retry hook is what stops that cycle during peak.

## Install

```sh
opencode plugin add git+https://github.com/lutzkind/opencode-offpeak.git#v0.1.3
```

Then restart OpenCode (a long-running TUI keeps its old code until it restarts).

## Checks

- `npm run lint`, `npm run typecheck`, `npm test` (52 tests), `npm pack --dry-run`.
- Deterministic regression tests cover: the retry veto during peak, the queue task moving to `WAITING_OFFPEAK` and completing in the same session after the boundary, the interactive recovery delivered exactly once in the same session, location-scoped recovery persistence across an engine restart, a new session request superseding a pending recovery, non-retryable failures staying `FAILED`, OFF/`queue`/`guard` passivity, UNTRACKED/UNKNOWN pass-through, and the `run-now` override case.
- Isolated end-to-end run on the real OpenCode 2.0.27 binary with a local fixture provider that withholds response headers until the window ends: a queued task and an interactive message were sent during off-peak, failed retryably after crossing into peak, were vetoed (no further retry events), produced **zero provider requests during the entire peak window**, stayed `WAITING_OFFPEAK`/`Recovery: 1`, and both continued in their **same sessions** at the boundary with the safe continuation prompt (no duplicate prompts or sessions).
